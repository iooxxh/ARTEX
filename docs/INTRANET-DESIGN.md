# 内网纵深能力架构设计（INTRANET-DESIGN）

> 状态：**架构指导文档，不含实现代码**。
> 本文档仅描述"做什么"和"为什么"，不涉及任何可执行的攻击代码
> （不含 webshell 马体、加密算法实现、绕过技术细节、监听器代码）。
> 具体实现需用户自行开发。
>
> 设计思路学习自 [focus-agent](https://github.com/XXXXXQ-0206/focus-agent)
> （基于 ARTEX 二次开发的内网纵深平台）的 session/tunnel/stage 模块架构。
>
> 适用范围：仅用于**已获得书面授权**的安全测试（HackerOne 项目 scope、
> 补天任务、客户授权的渗透测试）。内网横向超出授权范围即违法，
> 本架构把"授权检查点"作为硬性前置（见 §7）。

---

## 1. 定位与四阶段数据流

内网纵深解决的是"外网打点之后怎么办"：从一个外网立足点出发，
把网络位置推进到目标内网，做授权范围内的纵深验证。

四阶段与数据流：

```
阶段一：外网突破（现状）
  planner + worker 群打外网 Web 面
  产出：立足点（经 RCE 拿到的命令执行能力）
        │
        ▼  移交：立足点注册为平台管理的"会话资产"
阶段二：立足点运营
  会话抽象统一管理（session）
  产出：目标侧侦察数据（网卡/网段/路由）→ 新网段资产入库
        │
        ▼  硬性授权检查点：新网段 ≠ 有权打，必须人工确认 scope
阶段三：隧道前移（tunnel）
  探测 → 选型 → 部署 → 验证 → 健康检查
  产出：socks5 端点（网络位置前移），worker 流量经隧道进内网
        │
        ▼
阶段四：内网纵深
  凭据收割 → 复用打分 → 横向（经会话或隧道）
  产出：纵深 finding，循环直至目标达成
```

关键设计决策：**阶段二是"关联任务"**，继承黑板机制已存在；
scope=内网段，worker 工具面增加 session/tunnel 工具，
提示词切换为内网词汇。阶段一切换不是自动的，必须经过 §7 的授权闸门。

## 2. session：会话抽象（立足点一等管理）

### 2.1 为什么需要会话抽象

没有抽象时，目标侧命令执行散落在各处：webshell 靠 HTTP 请求、
反弹 shell 靠裸 TCP、SSH 靠另一套库。每种通道的"怎么连、怎么执行、
怎么传文件"都不一样，agent 代码里到处是 if-else。

会话抽象把"目标侧执行能力"收敛为**一个接口**，agent 只看到"会话工具"，
不关心底下是 webshell 还是 SSH。这是整个内网架构的地基：
tunnel 的部署、stage 的投递、阶段四的横向，全部经会话抽象调用，
不直接碰通道细节。

### 2.2 接口形状（设计层面）

```
Session {
  Test()                    // 存活探活：会话是否还可用
  Exec(cmd)                 // 执行命令，返回结构化结果（含错误语义）
  ExecStream(cmd)           // 流式执行（长输出/交互场景）
  ReadFile(path)            // 读目标文件
  WriteFile(path, data)     // 写目标文件
  Upload(local, remote)     // 上传文件（大文件分块）
  Close()                   // 关闭会话，清理资源
}
```

设计原则（只讲原则，不讲实现）：

- **断线诚实**：命令没执行就是没执行，返回带语义的错误，
  不伪造成功。这是确定性验证思想在内网的延伸——
  "无验证步骤永不可标已执行"。
- **回显防污染**：命令输出必须能和噪声区分开，
  否则 agent 会把提示符、banner 误读成命令结果。
- **agent 触达面是普通工具调用**：`register_session`（登记立足点）、
  `session_exec`、`session_read`、`session_write`、`session_list`。
  全部自动过 guard 审批、自动进 activity 留痕——
  这是相对"平台外通道"的本质优势：**所有目标侧动作都在平台账本里**。

### 2.3 落库与生命周期

- 新表 `sessions`：kind / 关联主机资产 / 连接参数（加密存储）/
  健康状态 / 心跳 / 创建意图。连接参数必须加密落库，明文存密钥是红线。
- 平台重启后恢复：长寿命会话（如监听器）重启时按台账恢复，
  而不是丢了就忘。
- 立足点策略（供用户决策时参考）：优先复用**入站通道**
  （复用已有的 HTTP 入站，无需目标出网），出网回连通道降级为
  临时使用、用完即收。原因是出网回连的前提"目标能连回平台"
  恰恰是最常被防火墙拦截的一环，且长连接流量特征明显。

## 3. tunnel：隧道编排（网络位置前移）

### 3.1 编排流程（六步）

```
probe（探测） → plan（选型/中继推导） → deploy（部署）
    → verify（隧道内决定性验证） → health（健康检查/自动重拉）
    → teardown（拆除，不留孤儿）
```

**probe——出网探测**：经会话在目标侧真实执行出网探针
（TCP 连通性、DNS 解析、HTTP 出网），回显用确定性标记解析。
输出是**结构化报告**，不是给模型看的自然语言。
判定是三态而非二态：连上 / 快速拒绝 / 超时——
"快速拒绝"（RST）证明路径是通的，只是对端暂无监听，
隧道监听该端口即可回连；只有"超时/无响应"才是真被过滤。
**探测结论决定选型**，选型规则进 chains L3 骨架。

**plan——中继推导**：输入是资产图里的网卡/网段数据，
输出是结构化的部署计划（ hops JSON）。
计划是**持久化单元**：整体序列化落库，断链重拉时反序列化
可直接重新部署，不丢任何参数。这是针对"只记状态不记参数，
重拉名存实亡"这一常见缺陷的修正。

**deploy——部署**：平台侧起隧道服务端（进程台账：pid/命令行/日志
全部登记）；客户端二进制经 stage 受管投递（见 §4）送到目标；
远端拉起。任一步失败**逐层回滚**，不留孤儿进程。

**verify——隧道内决定性验证**：本机"监听口起来了"不算通，
必须经隧道**真实拨测目标**才算 alive。
这是借鉴"反证"思想：不经验证的"通"一律视为不通。

**health——健康检查**：周期真实探活（平台侧进程 + 隧道入口可连 +
定期经隧道实际拨测）。死了标 error 并用持久化的部署参数
自动重拉（指数退避，有上限）。**死链绝不当活上游**——
把死链当活链用，agent 会在上面浪费整轮 token。

**teardown——拆除**：远端进程经会话按 pid 核对后杀
（必须核对 `/proc/<pid>/cmdline`，不能只看 pid，防止 pid 复用误杀）、
杀平台侧服务端、删 stage 条目、状态置 stopped。
任务停止/进程退出时由 manager 兜底调用。

### 3.2 隧道消费：录制链不断

隧道建成 = 一个 socks5 端点。worker 的代理注入从"全局唯一"
扩展为**按任务（或按意图）绑定上游**：worker 的 Bash 流量 =
本地 MITM 录制代理 → socks5 隧道 → 内网目标。

这是架构上最关键的一点：**录制与隧道在拓扑上天然串联**，
本地 MITM 仍然录到全部流量，证据链不断。
agent 侧只见 `tunnel_*` 工具，**不允许用裸 Bash 自起隧道进程**
（会被端口审计发现，由"受管资源"兜底收割，见 §4）。

### 3.3 多层中继

双网卡主机的第二网段、经 alive 上游逐跳推进——
中继推导是算法问题（输入资产图，输出 hops），
上游活性必须**真实探活**，不能只信数据库里的 status 字段。

## 4. stage：受管文件投递暂存

### 4.1 解决的问题

AI 起临时 HTTP 服务投递文件后"忘关"，导致投递服务变成
对全网开放的孤儿——目录里常混有战利品凭据。
根因不是 AI 记性差，而是**资源在平台账本之外**：
临时 HTTP 服务是一条 Bash 命令的副作用，平台零感知。

### 4.2 受管资源原则（架构铁律）

> **凡带外部暴露面的资源——HTTP 暂存、隧道进程、反弹监听、
> 临时防火墙规则——必须由平台登记台账、强制 TTL、归属任务、
> 平台回收。没有例外。**

prompting is not enforcement，必须用机制，不用提示词约束。

### 4.3 投递服务设计原则

- **随机 token 路径**：`/s/<token>/<name>`，token 足够长且随机，
  无目录列举。下载路径无需鉴权（目标机器没有平台 token），
  靠"随机 token + 每 token 速率限制"防枚举；
  错误 token 与不存在路径的**响应逐字节一致**，不泄露存在性。
- **硬 TTL**：默认 15 分钟到期自动销毁（上限可配，如 2 小时），
  支持一次性下载即焚。
- **默认最小暴露面**：默认只绑 loopback，需对目标可见时
  才绑指定接口或走隧道。
- **全程记账**：谁投递、何时过期、被何源 IP 拉走，全部进 activity。
- **投递分级（制度红线）**：暂存只用于**向外投递工具**；
  战利品/凭据回流一律走会话读取或 evidence 存储。
  制度上保证：即使暂存服务被打穿，也没有敏感数据可泄。
- **堵野路子**：guard 内置不可删除规则，拦截
  `python -m http.server` / `php -S` 之类的临时起服务行为，
  拦截理由写明"请改用受管投递"。**正道比野路子好用，
  绕过动机自然降低**——这是比单纯拦截更高明的治理。
- **兜底收割**：worker 的 Bash 跑独立进程组，意图结束/任务停止
  整组收割；定期扫描本机监听端口，台账外监听者告警、
  可配自动 kill。

## 5. 数据模型扩展思路

内网能力需要资产模型升级（这是"最大的手术"，建议独立排期）：

- **host 实体**：多个 ip/nic 资产归并到 host 下
  （nic 表：ip + segment + iface）。双网卡归并靠"同一会话上报的
  网卡信息"或 MAC/主机名指纹。现状是一个 IP 全局一行，
  双网卡主机会被拆成两条互不相干的资产。
- **网段实体**：`segments`（cidr + 经哪条链路可达）。
- **链路边**：新表 `links`（kind=socks/portfwd/relay、
  src_host/dst_segment、state、deploy_params）。
  **链路是跨任务的全局事实，属于资产图**，不要塞进探索边。
- **凭据一等实体**：新表 `credentials`（类型/加密 secret/
  来源主机/适用范围推断）。复用打分建议服务端规则 + LLM 双轨；
  **喷洒/爆破动作必须过 guard ask**（RoE 硬约束）。
- **覆盖度统计扩展**：分母从"task_scope 命中资产"扩展为
  "已发现网段中的存活资产"；covered 定义增加"经会话/隧道实测"。

## 6. 与现有 guard / RoE 的配合

本 fork 已有的防线（按 PreToolUse 执行顺序），内网模块按下述方式接入：

```
PreToolUse
  ├─ 1. checkEgress（出口审查）：命令全文扫平台密钥指纹
  │     → 内网模块新增：会话连接参数、隧道 auth token
  │       纳入指纹注册（只存哈希，不存原文）
  ├─ 2. 审计记录
  ├─ 3. checkRoE（范围审批 off/warn/strict）
  │     → 内网模块：新网段发现后，strict 模式下
  │       打新网段 = 范围外 = 进人工审批（见 §7）
  ├─ 4. checkTarpit（熔断）
  └─ 5. applyIntercept（用户拦截规则 + LLM 兜底裁判）
```

配合点明细：

1. **会话工具走完整 guard 链**：`register_session` / `session_exec` 等
   是普通工具调用，自动过 egress（防连接参数外泄）→ RoE
   （目标是否在 scope 内）→ 用户规则。不存在"后门通道"。
2. **高危写操作强制 ask**：立足点写入、隧道部署、文件投递、
   凭据喷洒——在 strict 模式下全部进人工审批。
   RoE 的三档语义在内网同样适用：off 关闭 / warn 只告警 /
   strict 范围外拦截。
3. **隧道 auth 凭据**：只存部署参数台账与平台侧受限权限文件，
   不出现在进程命令行（`ps` 不可见）。
4. **受管资源台账**：隧道进程、投递条目、监听器全部登记，
   settlement/任务停止时清理——与 §4.2 的兜底收割是同一套机制。
5. **蜜罐联动**：内网蜜罐更常见。honeydetect 的签名在内网同样生效；
   识别到蜜罐后单信号降级交互、双信号封锁方向（见蜜罐模块文档）。

## 7. 授权检查点（硬性前置，不可跳过）

**发现新网段 ≠ 有权打新网段。** 内网 RoE 与外网几乎必然不同
（HackerOne 的 scope 通常只覆盖外网资产；补天任务以任务书为准）。

流程：

1. worker 经会话侦察发现新网段 → 新网段资产入库（只读侦察不算越界，
   但建议也在 warn 以上）。
2. 任务进入"内网阶段"前：guard ask 弹出 + **人工确认**后，
   新网段登记进 `task_scope`。
3. 确认后才创建关联任务（scope=内网段），worker 工具面
   才开放 session/tunnel 工具。

**没有人工确认，内网工具面对 worker 不可见。**
这是架构层面的强制，不是提示词层面的"请注意 scope"。

## 8. 实施分期建议

| 期 | 内容 | 前置依赖 |
|---|---|---|
| 0 | 安全前置：RoE 代码强制、guard fail-closed | 无（本 fork 已有 RoE，可直接用） |
| 1 | session：会话抽象 + 落库 + `register_session`/`session_exec` 工具 + guard 覆盖 | 期 0 |
| 2 | 受管资源台账 + stage 投递服务 + 兜底收割 | 期 1 |
| 3 | tunnel：probe / plan / deploy / verify / health / teardown + 按任务代理绑定 | 期 1–2 |
| 4 | 阶段编排：授权检查点 + 关联任务模板 + 内网提示词 + chains L3 内网路由 | 期 3 |
| 5 | 数据模型扩展：host / segments / links / credentials | 期 1（可并行） |

期 1 完成后具备"立足点管理 + 目标侧执行"；
期 3 完成后具备"多层代理纵深"；期 4 完成后才是完整闭环。
